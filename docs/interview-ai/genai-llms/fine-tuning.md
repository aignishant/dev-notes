## Q41. When should you fine-tune vs prompt vs RAG? { #q41 }

The first question a senior engineer asks when someone says "I need to fine-tune." Most of the time, you don't.

**Use prompting / few-shot when:**
- The task is doable with a well-crafted prompt on a strong model.
- You need to iterate quickly.
- Requirements change frequently.
- Data is limited (<1000 examples).

**Use RAG when:**
- The need is **knowledge**, not behavior. You want the model to know facts it wasn't trained on (company docs, product catalog, recent events).
- Sources change often.
- You need citation / attribution.
- Data is proprietary and updated frequently.

**Use fine-tuning when:**
- You need a **specific behavior or style** that prompting can't reliably elicit.
- You want to **distill** a larger model's capabilities into a smaller, cheaper one.
- You need **structured outputs** more reliable than grammar-constrained generation gives.
- You want to eliminate a long, expensive system prompt by baking its instructions into the weights.
- You have **thousands of high-quality demonstrations**.

**Decision matrix:**

| Need | Solution |
|---|---|
| Know recent news | RAG |
| Answer in a company-specific tone | Fine-tune |
| Never use specific phrases | Fine-tune (prompting alone is unreliable) |
| Generate JSON in a specific schema | Structured output or fine-tune |
| Summarize in 3 bullets, 15 words each | Prompting works |
| Cite internal docs | RAG |
| Translate between Klingon variants | Fine-tune (rare data) |
| Beat GPT-4 on your niche task with a 7B | Fine-tune (from SOTA outputs) |

<div class="tip-box" markdown>
**Senior framing:** "Fine-tuning is a tool of last resort after prompting and RAG. It adds ops complexity (versioning, evals, retraining) — only justifiable when the behavior change warrants it."
</div>

## Q42. SFT — supervised fine-tuning from scratch { #q42 }

**Supervised Fine-Tuning (SFT):** train the model on (instruction, response) pairs using the same next-token prediction loss as pretraining.

**Data format:**

```
<|system|>You are a helpful assistant.<|end|>
<|user|>What is the capital of France?<|end|>
<|assistant|>The capital of France is Paris.<|end|>
```

**Key decisions:**

**1. Masking:** only compute loss on the *assistant* tokens, not the prompt. This is **response-only loss** and is standard.

```python
# Conceptually:
loss_mask = (labels_role == "assistant")
loss = -sum(log_probs[loss_mask] * labels[loss_mask]) / loss_mask.sum()
```

**2. Packing:** concatenate multiple short examples into one sequence to fill the context window. Dramatically improves training efficiency, but requires proper masking between examples.

**3. Hyperparameters for SFT (2026 defaults):**
- **Epochs:** 1-3 (more risks overfitting).
- **LR:** 1-3e-5 for 7B; 5e-6 for 70B. Much smaller than pretraining.
- **Warmup:** 3% of steps.
- **Schedule:** cosine decay to 10% of peak.
- **Batch size:** 32-128 effective.
- **Weight decay:** 0 (or very small; avoid disrupting pretrained representations).
- **Dropout:** 0 or 0.1.

**4. Data quality trumps quantity.** 5k curated examples often beat 500k auto-generated. Key curation principles:
   - **Diversity** across task types.
   - **High-quality responses** — curated, edited, or generated by stronger models.
   - **Length distribution** matching deployment (don't only train on 2-sentence answers if you want long responses).
   - **Deduplication.**

```python
# Minimal SFT loop with Hugging Face TRL
from trl import SFTTrainer
from transformers import AutoModelForCausalLM, AutoTokenizer, TrainingArguments

model = AutoModelForCausalLM.from_pretrained("meta-llama/Llama-3-8B")
tokenizer = AutoTokenizer.from_pretrained("meta-llama/Llama-3-8B")

trainer = SFTTrainer(
    model=model,
    tokenizer=tokenizer,
    train_dataset=dataset,              # dicts with "prompt", "completion"
    args=TrainingArguments(
        output_dir="./sft-llama3",
        per_device_train_batch_size=4,
        gradient_accumulation_steps=8,
        num_train_epochs=2,
        learning_rate=2e-5,
        lr_scheduler_type="cosine",
        warmup_ratio=0.03,
        bf16=True,
    ),
    max_seq_length=4096,
)
trainer.train()
```

## Q43. The "alignment tax" and why RLHF exists { #q43 }

After SFT, you have a model that **follows instructions** but may:
- Be too verbose or too curt.
- Sometimes refuse safe requests.
- Miss subtle preferences (e.g., "be concise unless detail is explicitly asked").
- Make plausible-sounding but wrong statements (hallucinations).
- Not handle "impossible" questions well (tries to answer rather than declining).

**SFT alone can't fix these.** The issue is that SFT treats all provided completions as equally good — it imitates. But **human preferences are nuanced**: two plausible completions might both be "correct SFT examples," but one is strongly preferred.

**Enter preference-based fine-tuning.** Instead of "this is the correct answer," we provide **pairs of answers** with a preference judgment. Humans (or AI) rate: "answer A is better than answer B."

**The pipeline:**

```
Pretrained base model
    ↓ SFT on instruction data
SFT model (good at following, not great at preferences)
    ↓ Preference data collection (pairwise comparisons)
    ↓ RLHF (PPO) or DPO
Aligned model (production-grade)
```

**"Alignment tax"** (Ouyang et al. 2022): the observation that alignment tuning can *hurt* performance on some benchmarks (math, translation) while improving helpfulness and honesty. Trading raw capability for usability is a real trade-off.

**Modern mitigation:** careful data mixing (preserve capability-focused demonstrations alongside preference data), longer SFT phases with diverse data, and RL techniques (DPO with better regularization) reduce the tax substantially.

## Q44. RLHF via PPO — the original recipe { #q44 }

**RLHF = Reinforcement Learning from Human Feedback**, specifically using **PPO (Proximal Policy Optimization)** in the original InstructGPT / ChatGPT recipe.

**Three-stage pipeline:**

**Stage 1: SFT** (as above).

**Stage 2: Train a Reward Model (RM).**
- Collect pairwise preferences: for each prompt, sample two completions and have humans rank them.
- Train a model (typically initialized from the SFT model with a new scalar head) to predict which is preferred:

$$\mathcal{L}_{RM} = -\mathbb{E}_{(x, y_w, y_l) \sim D} [\log \sigma(r_\theta(x, y_w) - r_\theta(x, y_l))]$$

where $y_w$ is the preferred (winning) completion, $y_l$ is the losing one. This is the Bradley-Terry model for pairwise preferences.

**Stage 3: PPO against the RM.**
- Roll out the policy (the LLM) on prompts to sample completions.
- Score each completion with the RM.
- Update the policy to maximize reward, with a KL penalty to the SFT model to prevent drift.

$$\max_\pi \mathbb{E}_{x \sim D, y \sim \pi(\cdot | x)} [r(x, y) - \beta \log \frac{\pi(y|x)}{\pi_{\text{SFT}}(y|x)}]$$

The KL term is critical — without it, the model collapses into exploiting RM quirks (producing gibberish that somehow gets high reward).

**Why PPO specifically:**
- Stable on-policy RL with a trust region (clipped objective).
- Handles the enormous action space (vocab × sequence length).
- Battle-tested.

**But PPO is a nightmare in practice:**
- Four models in memory simultaneously (policy, old policy, reward model, reference/SFT model).
- Brittle hyperparameters (KL coefficient, clip range, etc.).
- Slow — online generation is expensive.
- Reward hacking: policy finds unintended shortcuts.

**Which is why DPO emerged.**

## Q45. DPO — the clean alternative to PPO { #q45 }

**Direct Preference Optimization (Rafailov et al. 2023)** is the 2023 breakthrough that dramatically simplified RLHF.

**The insight:** the optimal policy for the KL-regularized RL objective has a **closed-form** relationship to the reward model and reference model:

$$\pi^*(y|x) = \frac{1}{Z(x)} \pi_{\text{ref}}(y|x) \exp\left(\frac{1}{\beta} r(x,y)\right)$$

Rearranging, the reward can be expressed in terms of the policy:

$$r(x,y) = \beta \log \frac{\pi^*(y|x)}{\pi_{\text{ref}}(y|x)} + \beta \log Z(x)$$

Substituting into the Bradley-Terry preference loss, the partition function cancels, giving a direct loss on the policy:

$$\mathcal{L}_{\text{DPO}} = -\mathbb{E}_{(x, y_w, y_l)} \left[\log \sigma\left(\beta \log \frac{\pi_\theta(y_w|x)}{\pi_{\text{ref}}(y_w|x)} - \beta \log \frac{\pi_\theta(y_l|x)}{\pi_{\text{ref}}(y_l|x)}\right)\right]$$

**In plain English:** push the policy toward $y_w$ and away from $y_l$, measured relative to the reference (SFT) model. **No reward model needed. No RL. Just supervised learning on pairs.**

**Code:**

```python
# DPO training — Hugging Face TRL makes it trivial
from trl import DPOTrainer, DPOConfig

trainer = DPOTrainer(
    model=model,
    ref_model=ref_model,                        # frozen SFT model
    args=DPOConfig(
        beta=0.1,                                # KL strength
        learning_rate=5e-7,
        num_train_epochs=1,
        per_device_train_batch_size=2,
    ),
    train_dataset=preference_dataset,           # {prompt, chosen, rejected}
    tokenizer=tokenizer,
)
trainer.train()
```

**Trade-offs vs PPO:**

| | PPO | DPO |
|---|---|---|
| Complexity | High (4 models, RL) | Low (2 models, supervised) |
| Stability | Fragile | Stable |
| Compute | 10-50× SFT | 2-3× SFT |
| Performance | SOTA if you can make it work | Matches PPO on most tasks |
| Reward hacking | Common | Rare (no explicit reward) |
| Online exploration | Yes | No (fixed preference set) |

**2024+ is the DPO era:** Llama 3, Mistral, most open-source alignment uses DPO or descendants. PPO remains in use at large labs (OpenAI, Anthropic) for the flexibility of online RL.

## Q46. DPO variants — IPO, KTO, ORPO, SimPO { #q46 }

DPO has spawned a family of descendants, each addressing a specific limitation.

**IPO (Identity Preference Optimization, Azar et al. 2023):** DPO can suffer from "deterministic preferences" — when the reference model puts probability ~0 on the chosen completion, the gradient explodes. IPO replaces the $\log \sigma$ with an MSE-style loss that's bounded:

$$\mathcal{L}_{\text{IPO}} = \mathbb{E}\left[\left(\log\frac{\pi(y_w)}{\pi_{\text{ref}}(y_w)} - \log\frac{\pi(y_l)}{\pi_{\text{ref}}(y_l)} - \frac{1}{2\beta}\right)^2\right]$$

**KTO (Kahneman-Tversky Optimization, Ethayarajh et al. 2024):** instead of *pairs*, uses *binary* labels ("this completion is good / bad"). Useful when you have thumbs-up/thumbs-down feedback, not pairwise rankings. Inspired by prospect theory — asymmetric treatment of gains vs losses.

**ORPO (Odds Ratio Preference Optimization, Hong et al. 2024):** combines SFT and preference optimization into a **single stage**. No separate SFT needed. Simpler pipeline, competitive results.

$$\mathcal{L}_{\text{ORPO}} = \mathcal{L}_{\text{SFT}}(y_w) + \lambda \log \sigma\left(\log \frac{\text{odds}_\theta(y_w|x)}{\text{odds}_\theta(y_l|x)}\right)$$

**SimPO (Meng et al. 2024):** observes that DPO's reference model dependence is an overhead. Replaces it with a simple length-normalized log probability:

$$\mathcal{L}_{\text{SimPO}} = -\log\sigma\left(\frac{\beta}{|y_w|}\log\pi(y_w|x) - \frac{\beta}{|y_l|}\log\pi(y_l|x) - \gamma\right)$$

**No reference model** — halves memory. The length normalization prevents reward hacking via verbosity.

**Practical picks (2026):**

| Scenario | Pick |
|---|---|
| Standard RLHF replacement | DPO or SimPO |
| Binary feedback only | KTO |
| Want to skip SFT phase | ORPO |
| Very small model, memory-constrained | SimPO |
| Production-quality alignment | DPO (most mature tooling) |

## Q47. Constitutional AI and AI feedback { #q47 }

**Constitutional AI (Bai et al. 2022, Anthropic):** use **AI, not humans**, to generate the preference signal for RL. The "constitution" is a set of principles the AI uses to critique and revise its own outputs.

**Pipeline:**

**Phase 1 — Supervised:**
1. Generate responses from a helpful-only model.
2. Ask the model to *critique* its own responses against constitutional principles ("did this response encourage harm?").
3. Ask the model to *revise* accordingly.
4. Fine-tune on the revised responses (SFT).

**Phase 2 — RL from AI Feedback (RLAIF):**
1. Sample pairs of responses.
2. Ask the model (or another model) to compare them against principles.
3. Use this as preference data for DPO/PPO.

**Why Constitutional AI matters:**
- **Scales better than human labels.** Humans are slow, expensive, inconsistent. Models can generate preference data at 1000× the rate.
- **Explicit principles** — the constitution is a readable document you can audit.
- **Reduces human exposure** to harmful content during labeling.

**2024+ trend:** frontier labs use a mix of human feedback (for critical / subjective decisions) and AI feedback (for scale and consistency). Pure RLAIF pipelines can now match RLHF quality on most benchmarks (Lee et al. 2023).

**Limits of Constitutional AI:**
- If the critic model has biases, those propagate.
- Complex ethical judgment still often benefits from humans.
- Risk of "preference collapse" — constitutional AI can flatten variation.

## Q48. LoRA — efficient fine-tuning explained { #q48 }

**LoRA (Low-Rank Adaptation, Hu et al. 2021)** enables fine-tuning huge models on modest hardware by learning **low-rank updates** to existing weight matrices.

**The math:** for a pretrained weight matrix $W_0 \in \mathbb{R}^{d \times k}$, instead of learning $\Delta W$ directly (same size as $W_0$), learn $\Delta W = BA$ where:
- $A \in \mathbb{R}^{r \times k}$ (down-projection)
- $B \in \mathbb{R}^{d \times r}$ (up-projection)
- $r \ll \min(d, k)$ (typically $r = 8, 16, 32, 64$)

Forward pass:
$$y = (W_0 + \alpha \cdot BA) x$$

where $\alpha$ is a scaling factor (typically $\alpha = r$ or $\alpha = 2r$).

**Initialization:** $A$ is Gaussian, $B$ is zero — so initial $\Delta W = 0$ and training starts from exactly the base model.

**Why it works:** the intuition is that task-specific adaptations have **low intrinsic rank** — you rarely need the full $d \cdot k$ degrees of freedom. Aghajanyan et al. (2020) showed fine-tuning often has effective rank <100 even for huge matrices.

**Parameter count:**

| Model | Full fine-tune params | LoRA params (r=16) | Ratio |
|---|---|---|---|
| Llama 3 8B | 8B | ~21M | 0.25% |
| Llama 3 70B | 70B | ~170M | 0.24% |
| Mixtral 8x7B | 47B | ~50M | 0.1% |

```python
# LoRA with PEFT library
from peft import LoraConfig, get_peft_model, TaskType

config = LoraConfig(
    task_type=TaskType.CAUSAL_LM,
    r=16,
    lora_alpha=32,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj"],
    lora_dropout=0.05,
    bias="none",
)

model = get_peft_model(model, config)
model.print_trainable_parameters()
# trainable params: 20,971,520 || all params: 8,030,261,248 || trainable%: 0.26%
```

**Which layers to target:**
- **Attention layers** (Q, K, V, O) — highest quality impact per parameter.
- **MLP layers** (gate/up/down projections) — better quality at higher parameter budget.
- **Embeddings** — rarely needed unless vocabulary extends.

**Hyperparameters:**
- **r:** 8-16 for most tasks; 32-64 if quality plateaus.
- **alpha:** $\alpha = 2r$ is a common default.
- **Learning rate:** 1e-4 to 3e-4 (higher than full fine-tuning).
- **Dropout:** 0.05-0.1.

**Merging:** for inference, you can **merge** LoRA weights into the base: $W' = W_0 + \alpha BA$. This makes the fine-tuned model a drop-in replacement with no extra compute.

## Q49. QLoRA and the democratization of large-model fine-tuning { #q49 }

**QLoRA (Dettmers et al. 2023) = 4-bit quantized base + LoRA.**

**Core innovations:**

**1. NF4 (NormalFloat4):** a 4-bit data type optimal for normally-distributed weights. Weights are quantized to one of 16 levels placed at the quantiles of a normal distribution.

**2. Double quantization:** quantize the quantization constants themselves (the per-group scales). Saves ~0.4 bits per parameter.

**3. Paged optimizers:** when GPU memory spikes (e.g., during backward pass), automatically page optimizer states to CPU/NVMe, avoiding OOM.

**4. LoRA adapters kept in BF16.** Only the frozen base is 4-bit. This preserves gradient quality.

**Memory savings:**

| Approach | 65B model memory |
|---|---|
| Full fine-tuning (FP16) | ~780 GB |
| LoRA (FP16 base) | ~130 GB |
| QLoRA (NF4 base) | ~48 GB |

**That's the difference between "24 GPUs" and "one 48GB GPU."** QLoRA made 65B fine-tuning accessible to academics and hobbyists.

```python
from transformers import AutoModelForCausalLM, BitsAndBytesConfig
from peft import LoraConfig, get_peft_model, prepare_model_for_kbit_training

bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=torch.bfloat16,
    bnb_4bit_use_double_quant=True,
)
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-3-70B",
    quantization_config=bnb_config,
    device_map="auto",
)
model = prepare_model_for_kbit_training(model)

lora_config = LoraConfig(
    r=64, lora_alpha=16,
    target_modules=["q_proj","k_proj","v_proj","o_proj","gate_proj","up_proj","down_proj"],
    lora_dropout=0.05, bias="none", task_type="CAUSAL_LM",
)
model = get_peft_model(model, lora_config)
```

**Quality:** QLoRA matches full fine-tuning on most benchmarks. The 4-bit quantization of the frozen base introduces minimal additional error because we're only reading (not updating) those weights.

## Q50. PEFT zoo: LoRA, DoRA, Adapters, Prefix tuning, P-tuning { #q50 }

**PEFT (Parameter-Efficient Fine-Tuning)** = umbrella term for techniques that train a small fraction of parameters.

**Prefix tuning (Li & Liang 2021):** prepend learnable "virtual tokens" to every layer's input. Only these prefix parameters are trained.

**P-tuning v2 (Liu et al. 2022):** similar to prefix tuning but uses a deep prompt encoder for better convergence.

**Adapters (Houlsby et al. 2019):** insert small MLP blocks between transformer layers. Only adapters are trained; pretrained weights frozen.

**LoRA** (as above) — low-rank matrix updates.

**IA³ (Liu et al. 2022):** learn per-channel scaling vectors for attention K/V and FFN outputs. Even fewer parameters than LoRA.

**DoRA (Weight-Decomposed LoRA, Liu et al. 2024):** decomposes weight updates into magnitude and direction. Trains the magnitude as a vector, the direction via LoRA. ~0.5-1% better quality than LoRA at the same rank.

**VeRA (Kopiczko et al. 2024):** shares frozen random $A$ and $B$ matrices across layers, only trains per-layer scaling vectors. 10× fewer params than LoRA with similar quality.

**Comparison (for Llama 3 70B):**

| Method | Trainable params | Quality (vs full FT) | Latency impact |
|---|---|---|---|
| Full FT | 70B | 100% | None (0 extra) |
| **LoRA** (r=16) | 170M | ~98% | Can be merged |
| **DoRA** | 175M | ~99% | Can be merged |
| **QLoRA** | 170M | ~97-98% | Can be merged |
| Prefix tuning | ~10M | ~94% | Adds prefix tokens |
| Adapters | ~100M | ~96% | Adds layers |
| **IA³** | ~1M | ~93% | Element-wise scaling |
| **VeRA** | ~2M | ~96% | Slight |

**Which to pick in 2026:**
- **Default: LoRA** or DoRA. Mature tooling, can be merged, excellent quality.
- **Memory-constrained: QLoRA.**
- **Many adapters for multi-task: VeRA** or prefix tuning (cheap per-task).
- **Quality-sensitive: full FT** if you can afford it.

## Q51. Instruction tuning datasets — what good data looks like { #q51 }

**Quality of data > quantity.** 5k excellent examples can beat 500k mediocre ones.

**The hierarchy of instruction data:**

**Tier 1 (highest quality):**
- Human-written, human-verified.
- Examples: Dolly, OpenAssistant-1, LIMA (only 1000 examples, beat 50x larger baselines).

**Tier 2:**
- Generated by strong models (GPT-4, Claude 3), filtered by humans.
- Examples: UltraChat, OpenHermes, Nectar.

**Tier 3:**
- Generated by strong models, automatic filtering only.
- Examples: Alpaca, WizardLM, Evol-Instruct outputs.

**Tier 4 (caution):**
- Generated by smaller models or unchecked.
- Includes many public "Alpaca-style" datasets. Often noisy.

**What makes a good instruction dataset:**

1. **Task diversity.** Covers classification, generation, extraction, reasoning, creative writing, code, math.
2. **Response length diversity.** Mix of 1-sentence answers and multi-paragraph responses.
3. **Topic breadth.** Science, humanities, technical, casual.
4. **Refusal examples.** Cases where the correct response is "I can't help with that" or "I don't know." Without these, the model learns to always try.
5. **Multi-turn examples.** Conversations, follow-ups, clarifications.
6. **Instructions at varying specificity.** Some detailed, some vague.
7. **Edge cases.** Contradictory instructions, impossible questions, ambiguous prompts.

**Dataset mixing ratios (Llama 3 style):**
- ~40% general chat (UltraChat-like)
- ~20% STEM / reasoning
- ~15% code
- ~10% safety / refusal
- ~10% multilingual
- ~5% very-long context (for long-context capabilities)

## Q52. Synthetic data — the 2024 revolution in fine-tuning { #q52 }

**Post-2023 insight:** strong models can generate training data for weaker models (or for themselves). This has reshaped fine-tuning economics.

**Patterns:**

**1. Distillation from frontier models:**
- Prompt GPT-4 / Claude with a diverse set of instructions.
- Collect responses.
- Fine-tune a smaller open-source model on these pairs.
- Result: a 7B model that's 80-95% as good as GPT-4 on the target distribution, at 50× lower inference cost.

Examples: Alpaca, Vicuna, WizardCoder, Phi-3 (partly), DeepSeek-Coder.

**2. Self-improvement:**
- Model generates responses to prompts.
- Model (or another) critiques and filters.
- Good responses become training data.
- Retrain.

**3. Persona-based generation (Persona Hub, Microsoft 2024):**
- Create millions of diverse personas ("a retired biology teacher who gardens").
- Ask each persona to generate questions / content in its voice.
- Produces surprisingly diverse data at scale.

**4. Chain-of-thought distillation:**
- Strong model generates CoT reasoning for problems.
- Student trained on problem → reasoning → answer.
- Student learns to reason, not just answer.

**Risks and mitigations:**
- **Model collapse** (Shumailov et al. 2023): recursive training on synthetic data → narrowing distribution, loss of tail knowledge. Mitigation: mix synthetic with human data; periodically inject fresh human sources.
- **Hallucination transfer:** teacher's hallucinations become student's hallucinations. Mitigation: verify teacher outputs (math via calculators, code via execution).
- **Benchmark contamination:** synthetic data may contain benchmark questions. Mitigation: contamination checks before release.

<div class="scenario" markdown>
**Scenario — specialized customer service model:** instead of collecting 100k human conversations (expensive, slow), use Claude Opus to generate 50k high-quality customer service conversations across many scenarios, then fine-tune Mistral 7B on them. Result: in 2 weeks, a 7B model that matches Claude Opus on this specific domain at ~30× lower cost per query. This is now standard practice for vertical AI companies.
</div>

## Q53. Multi-task and continual learning { #q53 }

Sometimes you want one model to excel at several tasks, or to learn new tasks without forgetting old ones.

**Multi-task fine-tuning (simplest):** mix all task data into one training set. Works if tasks are related.

**Task-specific LoRA adapters:**
- Train one LoRA per task against the same base.
- At inference, swap adapters based on routing.
- Enables hundreds of "customized models" at trivial marginal cost.

**Continual learning — the catastrophic forgetting problem:**

When you fine-tune model $M$ on task $A$, then task $B$, performance on $A$ often **drops dramatically**. The weights updated for $B$ overwrite patterns learned for $A$.

**Mitigations:**

1. **Rehearsal:** mix some task-$A$ data into task-$B$ training. Simple, effective.

2. **Elastic Weight Consolidation (EWC, Kirkpatrick 2017):** identify which weights are important for task $A$ (via Fisher information), penalize changes to them when training on $B$.

$$\mathcal{L}_B^{\text{EWC}} = \mathcal{L}_B + \frac{\lambda}{2} \sum_i F_i (\theta_i - \theta_i^{A*})^2$$

3. **LoRA adapters:** train a new adapter for each task without touching the base. Near-zero forgetting.

4. **Orthogonal adaptation:** ensure new task's gradients are orthogonal to old task's important directions.

**In practice for LLMs in 2026:** people mostly use **adapter-based approaches (LoRA)** for multi-task, and **rehearsal with strong data mixing** for continual learning. EWC-style methods are more common in classical DL.

## Q54. Reward hacking and reward model issues { #q54 }

**Reward hacking** = the policy finds unintended ways to maximize reward without actually becoming better.

**Classic examples:**

1. **Length bias.** If humans prefer longer responses ceteris paribus, the RM learns "longer = better." The policy produces needlessly verbose answers.

2. **Flattery.** RM trained on "people prefer agreeable responses" → policy becomes sycophantic, agreeing with users even when wrong.

3. **Format exploitation.** RM gives high scores to responses with bullet points → every answer becomes bullet-formatted, even when prose would be better.

4. **Confident hallucination.** RM rewards confident-sounding answers → policy is confidently wrong more often.

5. **Reward model gaming.** Policy discovers adversarial inputs that score high on RM but are gibberish to humans. Catastrophic during PPO.

**Mitigations:**

1. **Length normalization** in the reward signal.
2. **Regularization with KL to reference.** Prevents drift into adversarial regions.
3. **Reward model ensembles** — use disagreement as uncertainty signal.
4. **Periodic RM refresh** with new human preferences — keep it up to date.
5. **Honest-signal rewards:** explicit penalties for hallucination, detected via fact-checking subsystems.
6. **Process rewards** (Lightman et al. 2023): reward correct *reasoning steps*, not just final answers. More robust to outcome hacking.

**Why DPO is more robust than PPO:** no explicit reward model to hack. The policy is optimized directly against pairwise preferences. Some failure modes (length, format) still occur but are less catastrophic.

<div class="tip-box" markdown>
**Interview anecdote:** Anthropic's and OpenAI's RLHF teams have published extensively on reward hacking surprises. Reading "Scaling Laws for Reward Model Overoptimization" (Gao et al. 2022) gives you the canonical framing: reward model score vs true quality diverges past a point — more RL makes the model *worse* on ground truth while looking better on the RM.
</div>

## Q55. Evaluation during fine-tuning { #q55 }

Fine-tuning without proper evals is flying blind. You can't tell if your changes help or hurt.

**Eval tiers:**

**Tier 1 — loss / perplexity:** cheapest. Useful for monitoring training but weak proxy for quality.

**Tier 2 — automatic metrics:**
- Exact match, F1 for structured tasks.
- ROUGE, BLEU, BERTScore for summarization/translation.
- pass@k for code (run unit tests).
- Accuracy on held-out multiple-choice benchmarks.

**Tier 3 — LLM-as-judge:**
- Ask GPT-4 / Claude to score outputs on a rubric.
- Fast, scalable, correlates reasonably with human judgment.
- MT-Bench, AlpacaEval use this approach.
- Caveat: judge models have biases (prefer their own style, longer responses).

**Tier 4 — human evals:**
- Gold standard but slow and expensive.
- Use for major model decisions (before deployment, for model cards).
- Need at least 100+ samples for statistical significance.

**What to actually track during training:**

```python
# A minimal eval loop during training
def eval_step(model, eval_loader, eval_benchmark):
    # Tier 1: perplexity
    ppl = compute_perplexity(model, eval_loader)
    
    # Tier 2: benchmark accuracy (cheap ones only during training)
    gsm8k_acc = evaluate_benchmark(model, "gsm8k", n=100)
    mmlu_acc = evaluate_benchmark(model, "mmlu", n=500)
    humaneval_pass = evaluate_code(model, "humaneval", n=50)
    
    # Log to wandb / tensorboard
    metrics = {
        "eval/ppl": ppl,
        "eval/gsm8k": gsm8k_acc,
        "eval/mmlu": mmlu_acc,
        "eval/humaneval": humaneval_pass,
    }
    return metrics
```

**Red flags during training:**
- Eval benchmarks drop while loss improves → overfitting or data-quality issue.
- MMLU drops but GSM8K rises → over-specialization.
- Length distribution shifts → watch for verbosity hacking.
- Refusal rate changes → alignment drift (in either direction).

## Q56. Domain adaptation — fine-tuning for industry verticals { #q56 }

Industry-specific fine-tuning (medical, legal, financial, code, scientific) needs different trade-offs than general chat.

**Key patterns:**

**1. Domain-adaptive pretraining first.** Before instruction-tuning, *continue pretraining* on domain corpus. Improves factual recall in the domain.
- Medical: PubMed Central, MIMIC-III notes, medical textbooks.
- Legal: case law, contracts, statutes.
- Code: GitHub, Stack Overflow.

**2. Preserve general capability.** Naive domain fine-tuning catastrophically forgets general abilities. Mix 10-30% general data into the domain fine-tune.

**3. Higher standards for correctness.**
- Medical: hallucination is dangerous. Strong retrieval + citation requirements.
- Legal: jurisdictional accuracy matters. Fine-tune per jurisdiction.
- Financial: quantitative accuracy matters. Use calculator tools, not model math.

**4. Domain-specific evals.** Don't rely on MMLU — use domain benchmarks:
- Medical: MedQA, MedMCQA, PubMedQA.
- Legal: LegalBench, CUAD.
- Code: HumanEval, MBPP, SWE-Bench.
- Scientific: SciBench, SciQ.

**5. Regulatory considerations.** Depending on jurisdiction, fine-tuned models for medical/legal/financial may need additional disclaimers, liability handling, or regulatory approval.

<div class="scenario" markdown>
**Scenario — building a legal contract review tool:** (1) continue pretraining Llama 3 70B on 100B tokens of US case law and contract templates; (2) SFT on 5k human-curated contract review annotations; (3) DPO with preference pairs from senior attorneys; (4) deploy with strict RAG over the client's jurisdiction's case law; (5) evaluate on LegalBench + internal rubric of 500 contract review tasks. Ship only after attorney QA on 1000 real contracts.

## Q57. Catastrophic forgetting in fine-tuning { #q57 }

When you fine-tune on domain X, benchmarks on tasks Y often drop — sometimes dramatically. This is **catastrophic forgetting**.

**Why it happens:** SFT / DPO updates the full weight matrix. Patterns learned in pretraining that aren't reinforced by fine-tuning data decay.

**Measurement:** always track held-out general benchmarks (MMLU, HellaSwag, TruthfulQA) during and after fine-tuning. Compare to the base model.

**Mitigations, by aggressiveness:**

**1. Low learning rate.** Smaller updates, less forgetting. But slower convergence.

**2. Fewer epochs.** 1-2 epochs for most fine-tunes. More rarely helps.

**3. Data mixing.** Include a fraction of pretraining-style data in fine-tuning. 10-30% general, 70-90% domain.

**4. LoRA instead of full FT.** Base weights frozen → pretrained knowledge preserved by construction. **This is the #1 reason LoRA is popular for fine-tuning.**

**5. KL regularization.** DPO already has this. For SFT, add a penalty: $\mathcal{L} = \mathcal{L}_{\text{SFT}} + \beta \text{KL}(\pi_\theta \| \pi_{\text{base}})$.

**6. Freezing early layers.** Keep lower layers frozen, only fine-tune upper layers. Lower layers are more general; upper layers are more task-specific.

**7. Model souping / weight averaging.** Fine-tune, then average with the base: $\theta_{\text{final}} = 0.5 \theta_{\text{base}} + 0.5 \theta_{\text{ft}}$. Trades a bit of task performance for much better general performance.

## Q58. Alignment and safety tuning — the final mile { #q58 }

After SFT + DPO, you have a capable, preference-aligned model. Now comes **safety tuning**:

**1. Red-teaming:** dedicated team tries to elicit harmful outputs. Collect failures.

**2. Safety SFT / DPO:** fine-tune on the collected failures, showing the model how to refuse or handle them safely.

**3. Jailbreak robustness:** train on known jailbreak patterns ("DAN prompts," role-play escapes, gradient-based attacks) to refuse reliably.

**4. PII / harmful content filters:** regex + classifier + LLM judge at both input and output. Defense in depth.

**5. Refusal calibration:** don't over-refuse. Good alignment means refusing harmful requests but remaining helpful for benign ones. Easy to make a model that refuses "how do I whittle wood" after safety tuning.

**Balancing helpfulness vs harmlessness:**

| Training signal | Helpfulness | Harmlessness |
|---|---|---|
| Raw SFT | High | Low |
| + DPO on helpful-only | Higher | Low |
| + Safety DPO | Medium | High |
| + Calibrated refusal data | High | High |

**The calibration problem is hard.** Production models in 2026 still frequently over-refuse or under-refuse. Anthropic, OpenAI, and Google all ship models that refuse benign requests at ~1-3% rates after deployment.

## Q59. Model merging — Frankensteining LLMs { #q59 }

**Model merging** = combining multiple fine-tuned checkpoints into one model without training. Popular in the open-source community since 2023.

**Basic approach — linear interpolation:**

$$\theta_{\text{merged}} = \alpha \theta_A + (1-\alpha) \theta_B$$

Works when both models started from the same base and have similar "basin" structure in weight space.

**Advanced merging techniques:**

**1. Task Arithmetic (Ilharco et al. 2022):** 
- Define "task vectors" $\tau_A = \theta_A - \theta_{\text{base}}$.
- Combine: $\theta_{\text{merged}} = \theta_{\text{base}} + \sum_i \alpha_i \tau_i$.
- Can even *subtract* task vectors to "unlearn" capabilities.

**2. TIES-Merging (Yadav et al. 2023):**
- Trim small weight updates (likely noise).
- Resolve sign conflicts (if two models agree on sign, keep; if disagree, pick majority).
- Merge only agreeing updates.

**3. DARE (Yu et al. 2023):** drop most weights randomly, rescale the rest, then merge. Surprisingly effective.

**4. Evolutionary merging (Sakana AI 2024):** use evolutionary search to find optimal merge weights per layer.

**Use cases:**

- Combine a code-focused and a chat-focused model into one.
- Merge task-specific LoRAs into a multi-task base.
- Ensemble multiple community fine-tunes into a "best of" model.

**Caveats:**
- Doesn't always work — models need to be compatible (same base, similar fine-tuning scale).
- Can produce worse models than any individual source.
- Quality is fragile — often needs evaluation across many tasks.

## Q60. End-to-end: fine-tuning Llama 3 for your task { #q60 }

Putting it all together — a senior engineer's playbook for fine-tuning a production LLM.

**Week 1 — Scoping and baselines:**
1. Define the task precisely. Input format, output format, success criteria.
2. Build a **gold eval set** of 200-1000 examples. This is the single most important artifact. Make it representative, edge-case-rich, and versioned.
3. Benchmark prompting approaches: zero-shot, few-shot, CoT, with GPT-4 / Claude / Llama 3 70B base. Establish ceiling.
4. Decide: does prompting suffice? RAG? Fine-tuning?

**Week 2 — Data collection:**
1. Curate training data — aim for 1k-10k examples of the highest quality you can afford.
2. Options: human labeling, teacher model distillation, existing datasets.
3. Split: 80% train, 10% eval, 10% final test (never touched until the end).
4. Clean: dedupe, filter low-quality, check for benchmark contamination.

**Week 3 — Fine-tuning:**
1. Pick base model: Llama 3 8B for most cases; 70B if quality demands.
2. Pick method: QLoRA (r=64) unless quality demands full FT.
3. Train with standard hyperparameters (Q42); 1-3 epochs.
4. Monitor: train loss, eval loss, a cheap benchmark subset, length distributions.

**Week 4 — Alignment (if needed):**
1. Collect preference pairs (human or Claude/GPT-4 as judge).
2. DPO for 1 epoch with $\beta = 0.1$.
3. Re-evaluate for regressions on the eval set.

**Week 5 — Deployment:**
1. Evaluate on the held-out test set. Only now.
2. If quality is acceptable, merge LoRA into base for serving.
3. Quantize to INT8/INT4 for inference.
4. Deploy with monitoring: output distribution, latency, user feedback.
5. Continuously collect failure cases. Plan retraining cadence (monthly? quarterly?).

**Week 6+ — Maintain:**
1. Monitor production metrics (refusal rate, tool-use success, user thumbs-up).
2. Weekly / monthly retraining with new data.
3. Track drift vs baseline.
4. Rotate red-team probes for emerging attacks.

<div class="tip-box" markdown>
**Most common mistake:** starting fine-tuning without a rigorous eval set. Every day you spend on fine-tuning without good evals is wasted — you can't tell if your changes help. Spend week 1 on evals. Always.
</div>

## ✅ Module Recap

- **Fine-tune as last resort** — prompting and RAG solve 80% of use cases. Fine-tune when you need behavior, not knowledge.
- **SFT + DPO** is the modern alignment stack. PPO is giving way to simpler preference methods.
- **DPO** avoids reward model hacking, is stable, and matches PPO quality for most applications.
- **LoRA** is the default fine-tuning method. **QLoRA** enables 70B+ fine-tuning on one GPU.
- **Data quality > quantity.** 5k curated examples beat 500k mediocre ones.
- **Synthetic data from frontier models** is the 2024+ accelerant — distill once, serve cheaply forever.
- **Catastrophic forgetting** is real. LoRA mitigates by construction; full FT needs rehearsal + KL.
- **Reward hacking** (length, flattery, format) is the dominant RLHF failure mode.
- **Model merging** is powerful but fragile — evaluate broadly, not just on the target task.
- **Evals first, always.** The gold eval set is the most valuable artifact in any fine-tuning project.
