01 — Cloud Computing Fundamentals

Q: What is cloud computing and why do organizations adopt it?

Cloud computing is the on-demand delivery of compute, storage, database, networking, and other IT resources via the internet with pay-as-you-go pricing. Instead of owning physical data centers, you rent capacity from a cloud provider.

5 Key Characteristics (NIST Definition)

  • On-demand self-service — provision resources without human interaction with the provider
  • Broad network access — accessible over the network via standard mechanisms
  • Resource pooling — provider resources are pooled to serve multiple consumers (multi-tenant)
  • Rapid elasticity — scale up/down automatically based on demand
  • Measured service — resource usage is monitored, controlled, and billed

IaaS vs PaaS vs SaaS — Deep Comparison

Interview Tip — How to Answer

"We choose the service model based on the level of control we need versus the operational overhead we want to accept. For a legacy app that requires specific OS configs, IaaS. For a new microservice, PaaS or FaaS to let the team focus on business logic."

This is the #1 most asked foundational question. The cloud provider secures the infrastructure "security OF the cloud", and the customer secures what they put in it "security IN the cloud".

🎯 Scenario Question

"Your company's EC2 instance was compromised via an unpatched CVE. Who is responsible?"

Answer: The customer. With IaaS, OS patching is the customer's responsibility. The fix: use AWS Systems Manager Patch Manager for automated patching, enable Amazon Inspector for vulnerability scanning, and use a golden AMI pipeline that bakes patches into base images.

Q: Explain Regions, Availability Zones, and how they affect architecture decisions

A Region is a geographical area containing multiple isolated data center clusters. An Availability Zone (AZ) is one or more discrete data centers within a region, each with independent power, cooling, and networking, connected via low-latency links.

Architecture Decision Matrix

  • Single AZ — Dev/test only. No HA. Cheapest.
  • Multi-AZ — Production standard. Survives single AZ failure. RDS Multi-AZ, ALB across AZs.
  • Multi-Region — Disaster recovery, low-latency for global users. Active-Active or Active-Passive.
🎯 Scenario Question

"Your application serves users in US, Europe, and Asia. Latency must be under 100ms. Design the region strategy."

Answer: Deploy in 3 regions (e.g., us-east-1, eu-west-1, ap-southeast-1). Use Route 53 latency-based routing (AWS) or Cloud DNS geo-routing (GCP) or Traffic Manager performance profile (Azure). Place a CDN (CloudFront/Cloud CDN/Front Door) in front for static assets. Database: use global tables (DynamoDB Global Tables / Cosmos DB multi-region writes / Spanner) for sub-100ms reads everywhere. Cache with regional ElastiCache/Memorystore clusters.

Q: What factors drive region selection?

  1. Data residency & compliance — GDPR requires EU data stay in EU
  2. Latency to end users — deploy close to your customers
  3. Service availability — not all services are in all regions
  4. Cost — pricing varies by region (US typically cheapest)
  5. Disaster recovery — DR region should be geographically distant

Q: Explain the CAP theorem and its relevance to cloud architecture

The CAP theorem states that a distributed system can guarantee only 2 of 3 properties simultaneously:

  • Consistency (C) — every read returns the most recent write
  • Availability (A) — every request gets a response (even if stale)
  • Partition Tolerance (P) — system operates despite network partitions

Since network partitions will happen in the cloud, you really choose between CP (consistent but may be unavailable during partition) or AP (available but may return stale data).

🎯 Scenario Question

"You're designing an e-commerce cart system. Should you choose CP or AP? Why?"

Answer: For the cart, choose AP — it's more important that customers can always add items (availability) even if they briefly see a slightly stale cart. For the inventory/payment service, choose CP — you cannot oversell products. Use DynamoDB with eventual consistency for the cart, and RDS/Aurora with strong consistency for inventory deduction and payment processing.

Q: What is eventual consistency and when is it acceptable?

Eventual consistency means that if no new updates are made, all replicas will eventually converge to the same value. The window is typically milliseconds to a few seconds.

Acceptable for: user profile images, social media feeds, analytics dashboards, product recommendations, DNS propagation

Not acceptable for: financial transactions, inventory counts, authentication tokens, leader election

Q: Explain RTO and RPO

  • RTO (Recovery Time Objective) — maximum acceptable downtime. "How fast must we recover?"
  • RPO (Recovery Point Objective) — maximum acceptable data loss. "How much data can we afford to lose?"

DR Strategy Spectrum (Cost vs Speed)

🎯 Scenario Question

"Your healthcare client requires RTO of 15 minutes and RPO of 1 minute. Budget is moderate. Which DR strategy?"

Answer: Warm Standby. Run a scaled-down replica in a secondary region. Use continuous database replication (Aurora Global Database with <1s lag, or Cloud SQL cross-region replica). On failover: Route 53 health checks trigger DNS failover, Auto Scaling scales up the warm standby to full capacity. This meets the RPO (<1 min with continuous replication) and RTO (minutes to scale up). Pilot Light would be cheaper but risks exceeding the 15-min RTO due to scale-up time.

Q: What does "stateless" mean and why is it critical for horizontal scaling?

A stateless application stores no session data locally. Every request can be handled by any instance. This is required for horizontal scaling because a load balancer can route requests to any backend.

How to make an app stateless:

  • Store sessions in Redis / DynamoDB / Memorystore (not local filesystem)
  • Store uploads in S3 / GCS / Blob Storage (not local disk)
  • Use JWT tokens instead of server-side sessions
  • Externalize configuration (environment variables, Parameter Store, Consul)

Q: How do you calculate Total Cost of Ownership (TCO) for cloud migration?

TCO factors to include:

  • Compute costs (instances, serverless invocations)
  • Storage costs (volume, tiers, egress)
  • Licensing (bring-your-own vs cloud-included)
  • Data transfer costs (often the hidden surprise — egress is expensive)
  • Staff costs (fewer ops engineers, but need cloud architects)
  • Training & certification
  • Migration costs (one-time)
  • Reduced downtime costs (improved HA/DR)
🎯 Scenario Question

"The CFO says 'the cloud is more expensive than our on-prem data center.' How do you respond?"

Answer: On-prem costs are often underestimated because they exclude power, cooling, physical security, hardware refresh cycles, over-provisioned capacity sitting idle 70% of the time, and the opportunity cost of engineers managing hardware instead of building product. A proper TCO analysis includes all of these. Additionally, cloud provides agility value — the ability to spin up a new product in days instead of months. That said, cloud CAN be more expensive if not optimized. The key is implementing FinOps practices: reserved instances, right-sizing, auto-scaling, and tagging for cost accountability.

A Virtual Private Cloud (VPC) is a logically isolated section of the cloud where you launch resources in a virtual network you define. You control IP ranges, subnets, route tables, gateways, and security.

Q: Explain public vs private subnets

  • Public subnet — has a route to an Internet Gateway (IGW). Resources get public IPs.
  • Private subnet — no route to IGW. Resources access internet via NAT Gateway/Instance.

Best practice: Web/load balancer tier in public subnets. Application and database tiers in private subnets. This is the 3-tier architecture pattern.

# AWS: Create a VPC with public and private subnets
aws ec2 create-vpc --cidr-block 10.0.0.0/16 --tag-specifications 'ResourceType=vpc,Tags=[{Key=Name,Value=prod-vpc}]'

# Public subnet
aws ec2 create-subnet --vpc-id vpc-xxx --cidr-block 10.0.1.0/24 --availability-zone us-east-1a

# Private subnet  
aws ec2 create-subnet --vpc-id vpc-xxx --cidr-block 10.0.10.0/24 --availability-zone us-east-1a

# NAT Gateway for private subnet internet access
aws ec2 create-nat-gateway --subnet-id subnet-public --allocation-id eipalloc-xxx
🎯 Scenario Question

"Your private subnet instances can't reach the internet to download patches. What's wrong?"

Answer: Check: 1) Is there a NAT Gateway in a public subnet? 2) Does the private subnet route table have 0.0.0.0/0 → NAT Gateway? 3) Is the NAT Gateway's subnet route table pointing 0.0.0.0/0 → Internet Gateway? 4) Do the security groups allow outbound traffic? 5) Do NACLs allow outbound + return traffic? Most common miss: the NAT Gateway is placed in a private subnet instead of public.

🎯 Scenario Question

"Your EC2 web server in a public subnet can't receive traffic on port 443. Security group allows inbound 443 from 0.0.0.0/0. What else could be wrong?"

Answer: Check: 1) NACL — does it allow inbound 443 AND outbound ephemeral ports (1024-65535)? Since NACLs are stateless, you need explicit rules for both directions. 2) Route table — does the subnet have a route to the IGW? 3) Does the instance have a public IP or Elastic IP? 4) Is the instance's OS-level firewall (iptables/Windows Firewall) blocking 443? Stateless NACLs are the #1 gotcha.

Q: How do you connect two VPCs?

Option 1: VPC Peering

  • Direct 1:1 connection between two VPCs
  • No transitive routing (A↔B and B↔C doesn't mean A↔C)
  • Can be cross-region and cross-account
  • Good for: small number of VPCs (<10)

Option 2: Transit Gateway (AWS) / Cloud Interconnect (GCP) / Virtual WAN (Azure)

  • Hub-and-spoke model — single gateway connects all VPCs
  • Supports transitive routing
  • Connects VPCs, VPNs, Direct Connect in one place
  • Good for: enterprise with 10+ VPCs, hub-and-spoke topology

Option 3: PrivateLink / Private Service Connect

  • Expose a service in one VPC to another WITHOUT peering
  • Traffic stays on cloud backbone, never touches internet
  • One-directional: consumer → provider
  • Good for: SaaS providers exposing APIs, cross-account service access
# AWS Transit Gateway
aws ec2 create-transit-gateway --description "central-hub" \
  --options "AmazonSideAsn=64512,AutoAcceptSharedAttachments=enable"

# Attach VPCs
aws ec2 create-transit-gateway-vpc-attachment \
  --transit-gateway-id tgw-xxx \
  --vpc-id vpc-prod \
  --subnet-ids subnet-a subnet-b
🎯 Scenario Question

"You have 50 VPCs across 3 AWS accounts. Development teams need to access shared services (logging, monitoring, CI/CD) in a central VPC. Design the networking."

Answer: Use AWS Transit Gateway as a hub. Attach all 50 VPCs to the TGW. Create route table associations: shared-services VPC routes to all spokes, spokes route to shared-services only (not to each other for isolation). Use Resource Access Manager (RAM) to share the TGW across accounts. For the shared services themselves, use PrivateLink endpoints so services are consumed without full VPC connectivity. This gives you centralized management, isolation between dev teams, and scalable connectivity.

Key GCP advantage

🎯 Scenario Question

"Your API receives a mix of HTTP REST calls and raw TCP connections for a game server. You need static IPs for firewall whitelisting by partners. Which load balancer(s)?"

Answer: Use an NLB for the game server (L4 TCP, static IPs, ultra-low latency). Use an ALB behind the NLB for the REST API (path-based routing, host headers). Alternatively, use a separate NLB for TCP and ALB for HTTP. The NLB provides static Elastic IPs that partners can whitelist. In GCP, use a Network Load Balancer (TCP) + HTTP(S) Load Balancer. In Azure, use Azure Load Balancer (TCP) + App Gateway (HTTP).

🎯 Scenario Question

"You're migrating from an on-prem data center to AWS. You want to gradually shift traffic to verify the cloud deployment works. How?"

Answer: Use Route 53 weighted routing. Start with 95% on-prem / 5% AWS. Monitor error rates, latency, and user experience. Gradually increase: 90/10, 70/30, 50/50, then 100% AWS. Q: What is the Principle of Least Privilege?

Grant only the minimum permissions necessary to perform a task. This is the single most important security principle in cloud.

Implementation:

  • Start with zero permissions, add as needed
  • Use IAM Access Analyzer (AWS) / Policy Analyzer (GCP) / Access Reviews (Azure) to find unused permissions
  • Avoid * in resource or action fields
  • Use conditions (restrict by IP, MFA, time, tags)
  • Prefer managed policies over inline policies

Q: Explain KMS key hierarchy

Envelope encryption is used everywhere in cloud:

  1. You create a Customer Master Key (CMK) in KMS — never leaves KMS hardware
  2. CMK generates a Data Encryption Key (DEK)
  3. DEK encrypts your actual data
  4. The encrypted DEK is stored alongside the encrypted data
  5. To decrypt: KMS decrypts the DEK using the CMK, then DEK decrypts the data

Q: What are SCPs and how do they work with IAM policies?

Q: How do you design an effective alerting strategy?

Rules of Good Alerting

  1. Alert on symptoms, not causes — alert when users are affected (high error rate, high latency), not when CPU is at 80%
  2. Use SLOs (Service Level Objectives) — "99.9% of requests complete in under 300ms." Alert when burn rate threatens the SLO.
  3. Reduce noise — every alert should be actionable. If you snooze it, delete it.
  4. Severity levels — P1 (page engineer now), P2 (fix within 4 hours), P3 (fix next business day)

SLO-Based Alerting Example

SLO: 99.9% of API requests succeed within 300ms (allows 0.1% error budget)
Monthly budget: 43.2 minutes of downtime

Alert 1 (Fast burn): If error rate > 10x normal for 5 minutes → P1 page
  → You'll exhaust monthly budget in 7.2 hours
  
Alert 2 (Slow burn): If error rate > 2x normal for 1 hour → P2 ticket
  → You'll exhaust monthly budget in 36 hours

  • Implement SAGA pattern for distributed transactions

  • Don't rewrite from scratch — the "big bang rewrite" fails more often than it succeeds

  • Feature flags — toggle between monolith and microservice per feature
  • Shared nothing — each microservice must have its own database

Q: How do you migrate a production database with zero downtime?

Strategy: Continuous Replication (CDC — Change Data Capture)

  1. Setup replication — AWS DMS / GCP Datastream / Azure DMS
  2. Initial full load — copies all existing data to target
  3. Ongoing CDC — captures all changes in real-time
  4. Validate — compare source and target row counts, checksums
  5. Cutover — switch application connection string to target. Downtime: <1 minute (just a DNS or config change)

🎯 Scenario Question

"Your NAT Gateway costs are $15,000/month and you didn't expect this. Why and how do you fix it?"

22 — Multi-Cloud & Hybrid Strategies

Q: Should we go multi-cloud?

Legitimate Reasons for Multi-Cloud

  • Best-of-breed services — BigQuery for analytics + AWS for everything else
  • M&A — acquired company is on a different cloud
  • Regulatory — some governments require data on specific clouds
  • Vendor risk — negotiating leverage, avoiding total dependency

Bad Reasons (Be Honest About This)

  • "Avoid vendor lock-in" — multi-cloud adds 2-3x complexity. The cure is worse than the disease for most companies.
  • "It's the same thing on every cloud" — it's not. Every cloud has different APIs, networking, IAM, and operational quirks.

Architect's Position

"I recommend being cloud-native on your primary cloud and cloud-agnostic at the application layer (containers, Terraform, Kubernetes). This gives you 90% of the multi-cloud benefit at 20% of the complexity. True multi-cloud where workloads actively run on multiple clouds should be reserved for specific, justified use cases."

Pattern 1: Event Sourcing

                  → Notification Service reads event → sends email

🎯 Scenario Question

"Your team is debating: should the new notification service be Lambda-based or container-based on EKS? How do you decide?"

Answer: Decision framework: 1) Traffic pattern: Is it spiky with long idle periods? → Lambda (scale to zero saves money). Is it steady 24/7? → Container (Lambda gets expensive at high RPS). 2) Execution time: Under 15 minutes? → Lambda is fine. Longer? → Container. 3) Dependencies: Does it need to maintain persistent connections (WebSocket, database connection pools)? → Container. 4) Concurrency: Can you handle concurrent executions with your downstream services? Lambda can scale to 1000 concurrent instantly — will your database handle 1000 concurrent connections? 5) For a notification service: likely Lambda. It's triggered by events, processes quickly (send email/SMS), has variable traffic, and each invocation is independent. Use reserved concurrency to protect downstream services.

Q: Choreography vs Orchestration in microservices

ApproachHowProsCons
ChoreographyServices publish events, others react (EventBridge/Pub/Sub)Loosely coupled, easy to add new consumersHard to track full workflow, debugging nightmares
OrchestrationCentral coordinator manages workflow (Step Functions)Visible workflow, easy to monitor, handles retries/failuresSingle point of coordination, tighter coupling to orchestrator

Rule of Thumb

  • Use choreography when services are truly independent (e.g., analytics reacting to events)
  • Use orchestration when you need guaranteed execution order, error handling, and visibility (e.g., order processing, loan approval)
  • In practice: most systems use both. Orchestration for critical business workflows, choreography for cross-cutting concerns (notifications, audit, analytics)

25 — Advanced Security & Compliance

Q: What is Zero Trust and how do you implement it in cloud?

Zero Trust principle: "Never trust, always verify." Every request is authenticated and authorized regardless of network location.

Implementation Pillars

  1. Identity — Strong authentication (MFA, OIDC, short-lived tokens). No long-lived credentials.
  2. Device — Verify device health before granting access (Intune, CrowdStrike).
  3. Network — Micro-segmentation (K8s Network Policies, Security Groups). No implicit trust.
  4. Application — mTLS between services (service mesh). API authentication on every call.
  5. Data — Encrypt at rest + transit. Classify data. DLP policies.
  6. Visibility — Log everything. Detect anomalies. SIEM integration.

Cloud Implementation Example

Before Zero Trust:
  Office network → VPN → All AWS resources accessible

After Zero Trust:
  Any location → Authenticate via SSO (Okta) → Session token
  Token includes: user identity, device health, MFA status
  Each AWS service checks token + IAM role
  Service-to-service: mTLS via Istio (both sides present certificates)
  Network: VPC endpoints only, no public IPs on internal services
  Data: All encrypted, row-level security in databases
